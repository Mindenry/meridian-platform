# Security

The security model assumes the browser is hostile. Every authorisation decision
is made on the server, and every content query is scoped to a site.

## 1. Assets and trust boundaries

| Asset | Why it matters |
| --- | --- |
| Published content | Reputation and correctness; defacement is the main integrity risk |
| Unpublished drafts | Confidential plans and unreleased material |
| Leads and applications | Personal data (name, email, phone, CV) |
| User accounts and roles | Control over publishing and site access |
| Integration credentials | Access to Google properties if configured |
| Media uploads | Malware, stored XSS, and storage abuse |

Boundaries: public website ↔ API, Studio ↔ API, API ↔ database/Redis/S3, and
operators ↔ infrastructure. The public website has no privileged credentials.

## 2. Authentication

- Sanctum SPA cookie sessions; no bearer tokens are stored in `localStorage`.
- `SANCTUM_STATEFUL_DOMAINS` is restricted to the Studio origin. The public site
  is not stateful.
- Login validates active status and password hash, regenerates the session, and
  records `last_login_at`.
- Logout invalidates the session and regenerates the CSRF token.
- CSRF is enforced on stateful writes; the Studio retries once on `419` after
  refreshing the cookie.
- Login is limited to 5 attempts per minute per email + IP.

## 3. Authorization

Two independent checks are required for admin work:

1. **Site access** — `EnsureSiteAccess` verifies that the user's `role_user`
   assignment includes the requested site. Super administrators bypass the
   assignment check but are still audited.
2. **Permission** — `permission:` middleware checks a granular slug such as
   `pages.publish`. Permissions are resolved for the current site, so a user can
   publish on one site and only edit on another.

Service-level checks add context:

- Editors may edit their own drafts with `pages.edit_own`; editing someone else's
  page needs `pages.edit_all`.
- Published pages cannot be edited without `pages.publish`.
- Approve, request-changes, publish, schedule, and unpublish each re-check their
  permission inside `WorkflowService`, not only in the route.
- Media deletion requires `media.delete` and is refused while references exist.
- Public endpoints never accept a user identity and cannot reach drafts.

The frontend hides controls it knows are unavailable, but that is convenience
only. The E2E suite proves an editor receives `403` when calling approve/publish
directly.

## 4. Input handling

- Every write uses Laravel validation with explicit types, lengths, and enums.
- Page/editorial slugs are normalised server-side and checked for uniqueness per
  site + locale.
- Block payloads are validated against `BlockRegistry`; unknown types are rejected.
  Rich text is sanitised with Symfony HTML Sanitizer using an allow-list.
- `html_embed` blocks are sanitised and restricted; iframes are only allowed from
  an approved host list.
- JSON columns are decoded with casts, never concatenated into SQL.
- The only raw JSON query is a parameterised `like` on `props` for media usage.
- Pagination is capped (max 100), and public search requires at least two
  characters.
- Public form schemas drive validation, so a hidden or injected field cannot
  bypass required fields.

## 5. Output handling

- Vue escapes interpolated content by default.
- Rich text is rendered as sanitised HTML from the API; the frontend does not
  re-sanitise but relies on the server allow-list.
- JSON-LD is serialised with `<` escaped to prevent script breakout.
- API errors never include stack traces when `APP_DEBUG=false`.
- Media URLs are absolute and generated by the API; user-supplied URLs are
  validated before storage.

## 6. Upload security

- Allowed content types: JPEG, PNG, WebP, GIF, PDF (10 MB limit).
- MIME is sniffed from file content (`getMimeType`, `getimagesize`, `%PDF-` header),
  never trusted from the extension.
- Images below 16×16 px and invalid PDFs are rejected.
- Filenames are slugged and suffixed with a checksum; the original name is stored
  as metadata only.
- Files are stored outside the application root by default (`storage/app/public`
  via a symlink) or in an S3 bucket with a public-read policy limited to media.
- Uploads are rate limited to 30/minute per user.
- Deleting an asset removes known variant paths; a failed storage delete does not
  silently delete the database row.

## 7. Spam and abuse

Public forms combine:

- A honeypot field (`website`) that must stay empty.
- A minimum elapsed time; sub-1.2s submissions add to the spam score.
- Link-count heuristics.
- Per-IP rate limits (8/minute for forms and applications, 40/minute for search).
- Stored spam score; high scores are marked `spam` and do not create leads.

Job applications accept a CV upload with the same MIME and size checks. There is
no CAPTCHA; that is a deliberate demo trade-off documented below.

## 8. Transport, headers, and CORS

- CORS allows only configured origins and supports credentials only for those
  origins.
- `supports_credentials` is true because the Studio session requires it.
- nginx adds `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy`.
- Production should terminate TLS at the edge and set
  `SESSION_SECURE_COOKIE=true`, `SESSION_SAME_SITE=lax`, and HSTS.
- The API sets JSON content type and does not expose server versions.

## 9. Secrets and configuration

- `.env` is git-ignored; `.env.example` contains no live secrets.
- Compose defaults are demo values and are labelled as such. Rotate `APP_KEY`,
  database, MinIO, Meilisearch, and session secrets before shared use.
- Integration credentials are stored in `integration_settings.credentials` and
  should be encrypted at rest (`encrypted` cast or a secrets manager) before
  production use. The demo leaves them unset and reports `disconnected`.
- No credentials are logged. The audit trail stores actions, not secrets.

## 10. Auditing and monitoring

`audit_logs` records content creation, edits, submissions, approvals, publishing,
scheduling, unpublishing, media changes, and access changes with user, site, IP,
user agent, and metadata. The Studio exposes the trail to users with `audit.view`.

The health endpoint checks the database. Production should add:

- Error tracking with alerting.
- Failed-login and rate-limit dashboards.
- Queue and scheduler heartbeats.
- S3/storage usage alarms.
- Regular dependency audits (`composer audit`, `pnpm audit`).

## 11. Known gaps and demo boundaries

- Demo accounts share `Meridian!2026`; this is not acceptable outside a demo.
- No MFA, SSO, or password reset flow is implemented.
- No CAPTCHA or third-party bot detection.
- Reverb channel authorization is configured but not exercised.
- The demo does not include a WAF, DDoS protection, or managed secret storage.
- CV uploads are stored but not virus-scanned.
- Right-to-be-forgotten is a documented manual process, not an automated job.

These gaps are explicit so the project is not mistaken for a hardened production
deployment. The architecture leaves clear seams for each control.
